# AGENTS.md - developing the Ozone CLI

Development guide for this repo (Maven artifact `com.ozonehis:cli`,
command `ozone`). Written for human developers and equally usable by AI
coding agents - follow it when changing or extending the CLI. Read `README.md`
first for the user-facing behavior.

## Naming rules (strict)

- The user-facing command is `ozone`. In comments, strings, docs and commit
  messages, refer to the tool as **the Ozone CLI** - never bare "ozone" when it
  means the tool.
  Command invocations in prose are quoted: `'ozone resolve'`.
- Maven artifact `com.ozonehis:cli`; Java package `com.ozonehis.cli`; main
  class `com.ozonehis.cli.OzoneCli`. The distro's declaration file is `ozone.yml` at the distro root.
- Generated-file headers: `.env` starts with `# Generated by the Ozone CLI.`
  (portable-file note follows); `manifest.yml` starts with `# Generated by the
  Ozone CLI - do not edit. Regenerate with: 'ozone manifest'`; `resolved/*`
  start with `# Generated by 'ozone resolve' - do not edit. Regenerate with:
  'ozone resolve'`. Test fixtures must mirror these headers exactly.

## Architecture

`OzoneCli` parses args and orchestrates. The rest is small, single-purpose
classes in `com.ozonehis.cli`:

- `Model` - parses the compose project's `model.yml` (sections: `base`,
  `databases`, `apps`, `integrations`, `addons`, `operations`,
  `incompatibilities`, `deployment`); `mergeOverlay`
  applies the distro's `model-overrides.yml` (additive only).
- `Selection` - parses `ozone.yml` `selection:` section (apps list + addons map).
- `Resolver` - computes the compose-file chain and profiles from model +
  selection + resolved overlay, and the seed `owners` set (section-qualified,
  e.g. `apps.openmrs`): selected apps, activated integrations, enabled addons.
- `Plan` - the resolved deployment plan (apps, addons, chain, restore and
  backup invocations, `owners`).
- `EnvGen` - builds the `.env`. Merge order (later wins): code-level
  `vars.yml` -> distro `resolved/vars.yml` -> the model's
  `deployment:` section. Owner blocks under `apps:`/`integrations:`/`addons:`
  are merged only when the included-owners set contains them; that set is the
  plan's seeds expanded by the transitive `vars-from` closure declared in the
  vars files (block-level list of section-qualified names, edges from both
  vars sources combined; unknown target or cycle = loud error). All other
  sections (databases, operations, restic, section-level common/paths) are
  always merged, as is the whole `deployment:` section. The `.env` is
  portable: `HOST_NAME`/`DISTRO_PATH` are never stored in it.
- `DistroMerge` - the `resolve` command: merges parent `resolved/` with the own
  `ozone.yml` sections (`vars:`, `model-overrides:`) into `resolved/`
  (`MERGED_FILES = {vars.yml, model-overrides.yml}`) and records `info.yml` from `--project-*`.
- `YamlMerge` / `Yamls` - YAML merge and load/dump helpers.
- `ComposePaths` - resolves compose file paths by declaration: base-model
  files against the compose root, overlay-declared files against the distro
  dir. An overlay naming a base-model file is a loud error.
- `Display` - all console output. Glyphs have fixed meanings: ✓ confirmation,
  ● a row, 🔑 credentials, ℹ note - and mark only the final result output
  (validate/manifest/resolve confirmations, the fenced command, services,
  credentials). Tool logs (applied defaults, resolved selection, written
  artifacts, exit status) are plain lines via `Display.log`, no glyph.
  Rules/notes align to `RULE_WIDTH = 72`. The
  printed compose command is fenced between rules and must stay byte-exact
  (multi-line, one continuation line per prefix assignment - this format is
  intentional; do not "tidy" it). `up`/`down`/`backup`/`restore` execute the
  command by default (summary + command go to stderr, exit code is propagated);
  `--print` prints them on stdout instead. `info` prints only the summary.
  Step/diagnostic logs always go to stderr via a dedicated `Display`, keeping
  stdout for `--print` output.

## Core principles

- **No magic.** Declarations decide; never probe the file system, guess, or
  parse strings to infer intent. Anything ambiguous -> fail loudly. Errors are
  `IOException`s prefixed `ozone: ` with an actionable message (often citing
  the command to run, e.g. `ozone resolve --to <distro-dir>`).
- **Approval rules (strict, session-level).** Do not write code or modify any
  file without the user's explicit approval - describe the planned changes
  first and wait. Do not commit anything without the user's explicit approval.
  Reading, searching and running tests/builds are always fine.
- -do not code anything without explicit approval from me)
- Booleans: anything other than `true` (incl. `false`, empty) is false.
- YAML style in `vars.yml`/`ozone.yml`: one var per line; lists use block
  style, inline `[...]` only for lists of 1-2 items. Long single-line scalar
  values (comma-separated lists like ODOO_ADDONS) must stay on one line -
  YAML folding would corrupt them.
- Nothing is generated in source trees. `resolved/` (in `distro/`) is generated at
  build time; `.env` and `manifest.yml` (in `run/`, the compose root's
  parent) are generated at deployment. All are gitignored and exist only in built
  artifacts / at deployment.
- Merge semantics (YamlMerge): maps recurse, lists append, scalars
  child-wins, type conflicts = loud error. The `selection:` section is NOT
  merged - it replaces the parent's wholesale via the build-time file copy.

## Maven wiring (in the main Ozone repo - do not duplicate by hand)

- `maven-parent/pom.xml`: `ozone-yml` profile (activated
  by `${basedir}/ozone.yml`) with the `com.ozonehis:cli` dependency, "Copy local
  ozone.yml" (process-resources) and "Resolve the ozone.yml sections"
  (prepare-package; `exec:java`
  `com.ozonehis.cli.OzoneCli` with `resolve --from
  ${project.build.directory}/${ozone.artifactId}/distro --to
  ${project.build.directory}/${project.artifactId}-${project.version}/distro
  --project-name ${project.artifactId} --project-version ${project.version}
  --project-description ${project.description}`). The cli jar is excluded from
  "Copy OpenMRS modules to a temporary location" (`excludeArtifactIds cli`).
  The `cli.version` property itself is defined once in
  `maven-commons/pom.xml`.
- `distro/pom.xml` (root distro): same two executions, without `--from`, plus
  the `com.ozonehis:cli:${cli.version}` dependency.
- `info.yml`'s name/version/description come from the child's own Maven
  attributes; a child pom must declare its own `<description>` (otherwise
  Maven inherits the parent's - there is no way to detect that, by design).

## Build, test, smoke

The `ozone` launcher and its PATH helpers live in this repo at `bin/`
(`ozone`, `ozone-path.sh` for sh/bash/zsh, `ozone-path.fish` for fish); the
root Ozone build unpacks them into the artifact as `bin/*` next to
`bin/cli.jar` (the CLI jar), so a built Ozone zip runs `bin/ozone ...`
directly. The session-local dev shims `ozone-local.sh` / `ozone-local.fish`
(define an `ozone` shell function over `target/cli-*.jar`) are excluded from
the artifact; source them from this repo root to use the CLI built from source.

```
mvn clean package
java -jar target/cli-1.0.0-SNAPSHOT.jar \
  --compose-root src/test/resources/fixture/compose \
  --distro src/test/resources/fixture/distro --hostname demo.local validate
```

Runtime commands take `--project <artifact-dir>` (default: the current directory;
derives `run/docker`, `distro/`, outputs in `run/`; `--hostname` defaults to
`localhost`); `--compose-root`/`--distro` remain as explicit overrides for
non-standard layouts like the test fixtures.

Fixtures live in `src/test/resources/fixture/{compose,distro}`; tests in
`src/test/java/com/ozonehis/cli/` (`DistroMergeTest`, `ResolverTest`,
`EnvGenTest`, ...). When changing USAGE text, keep the command column aligned.
When changing generated headers, update the fixtures in the same commit.
