# Ozone CLI

The Ozone CLI (command `ozone`, Maven artifact `com.ozonehis:cli`) assembles the
Docker Compose command of an Ozone distribution from the compose project's
**model** and the distro's **selection**. It runs the compose commands (or only
prints them with `--print`). It also resolves the distro build's inheritance
chain at build time.

## Why it exists

Ozone HIS is one compose project, but it is deployed as many
distributions, on many machines, by different actors. Configuration is
therefore specified at distinct moments and places, each with its own owner:

#### Code level - owned by Ozone

What *can* run at all: the apps, integrations, addons and operations, and
the rules of how they combine, plus the default values of every variable.
This is shipped inside every artifact.

#### Distro level - authored by each distribution

What *this* distro runs and how it differs from its parent: which apps are
selected, which addons are enabled, its variable overrides, and any compose
additions of its own.

#### Build time - per distro, via Maven

The inheritance chain of a multi-level distro is flattened once, at build
time, and the distro's identity (name, version, description) is recorded. The
published artifact is therefore self-contained and ready to deploy.

#### Deployment time - per machine

The final environment, derived from the resolved chain and the selection.

#### Invocation - per run

The machine/deployment specific values (hostname, distro location), provided
with the invocation itself rather than stored, so generated files stay
portable across machines.

#### Run time

The services themselves, started by `docker compose`.

### --- 

This split is what makes the problem complex: the same deployment is described
by layers owned by different people at different times, and no single file can
answer "what will actually run here". The root requirements are:

- **Enable/disable apps and addons without touching compose
  files**: a distro only declares its selection; the CLI computes the exact
  compose file chain and profiles. Removing a service means omitting it from
  the selection, not editing compose files.
- **Flexible environment variable manipulation across all levels**: defaults
  from the product, overlaid by each distro level (parent to child, with
  explicit merge rules), plus deployment-time knobs and invocation-time values.
- **Multi-level distros**: root distro -> child -> grandchild. Because Maven
  knows the full dependency chain, the inheritance is resolved at build time;
  deployment then needs no Maven context, only the published artifact.

The Ozone CLI exists to be the single, explicit tool at the center of this: it
resolves the distro chain at build time and assembles the exact compose command
at deployment time - running it, or printing it with `--print`.

## The distro's `ozone.yml`

Everything the CLI reads and writes lives at the distro root. The distro's own
declaration is a single `ozone.yml` with one section per concern:

| File / section | Authored or generated | Role |
|---|---|---|
| `ozone.yml` `selection:` | authored | Which apps are selected and which addons are enabled. Replaces the parent's selection wholesale (build-time file overlay) - disabling a service is done here |
| `ozone.yml` `vars:` | authored | This distro's variable values. Merged over the parent's `resolved/vars.yml` (see merge rules) and laid over the compose project's `vars.yml` |
| `ozone.yml` `model-overrides:` | authored | Compose fragments this distro adds on top of the base model. Merged additively over the parent's `resolved/model-overrides.yml`. Never removes entries |
| `resolved/vars.yml` | generated by `ozone resolve` at build | Flattened vars chain - the only vars source read at deployment |
| `resolved/model-overrides.yml` | generated by `ozone resolve` at build | Flattened model overlay chain - the only model overlay source read at deployment |
| `resolved/info.yml` | generated by `ozone resolve` at build | Distro identity: `name` (the compose project name, from the build's `--project-name`, i.e. the artifactId), `version`, `description` |
| `.env` (distro root) | generated at deployment | The env file for `docker compose --env-file`. Portable: it never stores `HOST_NAME` or `DISTRO_PATH` - the printed command provides them |
| `manifest.yml` (distro root) | generated at deployment | Echoes `info.yml` and lists the compose files of the selection |

`resolved/`, `.env` and `manifest.yml` are generated - never edited by hand,
never committed (gitignored).

## The compose project

The compose root (in a built Ozone artifact: the unpacked `run/docker` dir)
carries the code-level defaults:

- `model.yml` - the base model: everything that *can* run (apps,
  integrations, addons, operations, database services, incompatibilities) and
  the rules of combination. Compose file paths in the base model are relative
  to the compose root. The four entry kinds:
  - `apps:` - the selectable applications, listed under `selection: apps:`.
    `keycloak` is the SSO app: selecting it enables SSO (its `sso:` override
    fragments of other entries are appended, `ENABLE_SSO=true`).
  - `integrations:` - never listed in the selection; they activate
    automatically when all their `requires:` apps are selected.
  - `addons:` - optional stack extras toggled in `selection: addons:`
    (e.g. `proxy: true`).
  - `operations:` - run by dedicated commands, not toggled: `backup` (ad-hoc,
    on a live stack) and `restore` (one-off, run before `up`).
- `vars.yml` - code-level variable defaults, in blocks mirroring the model
  (apps / integrations / addons / operations / databases).

## Merge rules (`ozone resolve`)

Merging the parent's `resolved/` files with this distro's own sources:

- maps merge recursively,
- lists are appended,
- scalars: the child's value wins,
- type conflicts (map vs list vs scalar): loud error, the build fails.

Paths in `vars.yml` `paths:` values and in `model-overrides.yml` compose file
lists are relative to the **distro dir**; an overlay may not declare a file
that belongs to the base model (loud error).

## Usage

In a built Ozone artifact the CLI is bundled as `bin/ozone` (a launcher for
the shipped `bin/cli.jar`). To use the bare `ozone` command, either source the
helper or export PATH yourself:

```
. ./bin/ozone-path.sh        # sh/bash/zsh; in fish: source ./bin/ozone-path.fish
                             # or simply: export PATH="$PWD/bin:$PATH"
ozone --compose-root ...    # then use 'ozone' directly
```

Elsewhere, run the jar directly: `java -jar cli-<version>.jar ...`.

### From the source tree (development)

Build the CLI and source the session-local shim - no artifact needed:

```
mvn package
. bin/ozone-local.sh        # sh/bash/zsh; in fish: source bin/ozone-local.fish
ozone --compose-root ...    # uses target/cli-*.jar, this session only
```

```
ozone resolve [--from <parent-distro-dir>] --to <distro-dir>
              [--project-name <n>] [--project-version <v>] [--project-description <d>]

ozone --compose-root <dir> --distro <dir> [--hostname <h>]
      [--scheme <http|https>] [--env-file <path>] [--manifest <path>]
      [--no-credentials] [--print] <up | down | backup | restore | validate | manifest | info>
```

- `resolve` (build time): merge the parent distro's `resolved/` files with this
  distro's own `ozone.yml` sections into `resolved/`, and record the
  `--project-*` identity as `resolved/info.yml`.
- `up` runs `docker compose ... up -d` for the selection; `down` runs `...
  down`; `backup` runs the ad-hoc backup chain on the running stack; `restore`
  runs the pre-computed restore command (run it before `up`). With `--print`,
  these four only print the command (and the services/credentials summary)
  instead of running it; `--print` has no effect on `validate`/`manifest`/`info`.
  `validate` runs all validation rules and prints nothing on success;
  `manifest` generates `manifest.yml` and `.env` and prints the summary (every
  other command regenerates them too). `info` only prints the services and
  credentials summary. All of these read `resolved/` + the `ozone.yml`
  `selection:` section only.
- `--compose-root` - the Docker Compose project location (required except for `resolve`).
- `--distro` - the distro location (required except for `resolve`).
- `--hostname` - required for `up`/`down`/`backup`/`restore`/`info`: the
  deployment's hostname, or the machine's IP for local runs (localhost breaks
  SSO, e.g. on macOS).
- `--print` - print the compose command instead of running it; the summary is
  printed on stderr when running, on stdout when printing.

The command is printed multi-line, fenced between rules, byte-exact for
copy/paste (with `--print`; when running, it goes to stderr and the command
executes directly, propagating docker compose's exit code):

```
DISTRO_PATH='<distro dir>' \
 HOST_NAME=<hostname> \
 docker compose \
  --project-directory <compose root> \
  -p <project name> \
  --env-file <distro>/.env \
  -f <compose file> \
  ... \
  up -d
```

## Examples

`ozone --help` prints the same examples.

Build time - resolve this distro's `ozone.yml` sections against its parent (run by
the Maven build; run by hand only to regenerate `resolved/`):

```
ozone resolve --from target/ozone/distro --to target/my-distro-1.0.0-SNAPSHOT/distro \
              --project-name my-distro --project-version 1.0.0-SNAPSHOT \
              --project-description 'My distro'
```

Deployment - from an unpacked Ozone artifact:

```
ozone --compose-root run/docker --distro distro --hostname demo.local up
ozone --compose-root run/docker --distro distro --hostname demo.local up --print
ozone --compose-root run/docker --distro distro --hostname demo.local backup --print
ozone --compose-root run/docker --distro distro --hostname demo.local down
ozone --compose-root run/docker --distro distro --hostname demo.local info
```

## Build wiring (Maven)

Child distros inherit the resolve step from `maven-parent` via the `ozone-yml`
profile (activated when the project has an `ozone.yml`): it copies the distro's
own `ozone.yml` into the assembled artifact and runs `ozone resolve`
against the parent Ozone zip unpacked in `target/`. The root Ozone distro
(`distro/pom.xml`) runs the same step without a parent. Nothing is generated
in source trees - only in the built artifact.

See `AGENTS.md` in this repo for the development conventions of the CLI
itself. Migrating an existing child distro from the old scripts/-based setup?
See `MIGRATION.md` in this repo.
